## Context

当前执行接口用查询参数 `case_id` 表达单条执行，`case_id` 为空则表示全量执行；规格预览、`execute_run` 和 `run_queue` 也沿用同一二态契约。前端 `useSuiteRun.start` 虽然接收用于初始化状态的 `caseIds`，真正请求仍只能发送一个 `case_id`。进度条还固定以 Suite 全部用例数为分母，因此现有单条执行已经可能显示错误比例。

Suite 登录准备会在解析目标用例时自动加入有效集合，并由 Orchestrator 先执行一次后再启动业务用例。人工确认规格通过 `run_event` 持久化，embedded 和 queue 最终共用 `execute_run`。

## Goals / Non-Goals

**Goals:**

- 用一个明确、可校验的用例 ID 列表贯穿预览、Run 创建、embedded、queue 和执行核。
- 复用现有 Run、Orchestrator、登录准备、Skill、人工确认和 SSE 机制。
- 保持现有全量和单条调用兼容，并避免空数组意外触发全量执行。
- 让前端进度使用后端确认的实际 Run 范围。

**Non-Goals:**

- 不保存命名用例集合或常用执行组合。
- 不支持跨 Suite 选择、分页选择或拖动调整执行顺序。
- 不改变 Suite 并发策略、登录状态生命周期或 Midscene 单用例执行逻辑。
- 不为部分执行创建多个独立 Run。

## Decisions

### 1. 使用可空 `case_ids` 表达执行范围

执行和规格预览请求新增 `case_ids: list[str] | null`：

- 未提供或 `null` 表示全量执行。
- 非空列表表示部分执行，单元素列表也属于合法部分执行。
- 显式空数组返回 400，不降级为全量。
- 重复 ID 或非当前 Suite ID 返回 400，避免调用方错误被静默修正。

现有查询参数 `case_id` 暂时保留。只提供它时在入口规范化为单元素列表；同时提供 `case_id` 与 `case_ids` 时返回 400，避免优先级歧义。新前端统一使用请求体 `case_ids`。

替代方案是继续在 URL 中重复传递 `case_id`，但这会让规格预览、approved specs 和 queue 序列化继续拥有不同契约，因此不采用。

### 2. 统一扩展有效用例解析器

`resolve_effective_cases` 从单个 `requested_case_id` 扩展为可空的 `requested_case_ids`。解析器先完整校验集合，再按 `list_by_suite` 返回的原始顺序筛选，最后按既有规则把登录准备用例放到第一位并去重。

API 创建 Run 前和执行核启动后都调用同一解析逻辑。前者给用户快速反馈并计算 `total_cases`，后者防止 queue 延迟执行期间 Suite 内容或登录设置变化导致越权或范围扩大。

### 3. 前端列表直接承载选择状态

Suite 用例表首列增加行复选框和表头复选框。选择状态使用 case ID 集合保存：

- 表头复选框只切换当前搜索筛选结果。
- 搜索变化不清除已选择但暂时不可见的用例。
- 复选框点击阻止行点击，避免同时打开详情抽屉。
- 无选择时主按钮为“执行全部”；有选择时为“执行所选 N 条”。
- Run 执行期间禁用选择和启动按钮。

执行确认弹窗接收统一的目标 ID 列表，并显示全量、单条或所选数量。抽屉单条执行也通过同一列表请求路径发送一个 ID，减少前端分支。

### 4. 规格预览与执行使用相同范围

规格预览请求发送相同的 `case_ids`。后端在翻译前解析有效集合，因此登录准备自动出现在审核列表首位。确认后的 specs 仍写入 `specs_approved` run event，Run 创建时只接受有效集合中的规格。

这样人工审核前后使用完全相同的目标范围，不需要新增规格存储模型。

### 5. queue 持久化列表并兼容旧任务

`run_queue` 新增可空 JSON 列 `case_ids`，通过 Alembic 迁移添加。新任务写入规范化后的列表；全量任务写入 null。worker 优先读取 `case_ids`，仅对迁移前或旧进程写入的记录回退到现有 `case_id`。

保留旧 `case_id` 列而不立即删除，避免部署升级时队列中已有单条任务失效。后续独立清理任务可在确认没有旧记录后移除。

替代方案是把选择集合只写入 `run_event`，但执行范围属于 queue 的必要输入，把它作为普通进度事件会弱化任务契约并增加缺失事件时误跑全量的风险。

### 6. 后端总数作为进度权威值

Run 创建时使用有效集合长度写入 `total_cases`。Orchestrator 的 `suite_start` 已携带同一个总数，前端 `useSuiteRun` 增加本次 Run 总数状态并监听该事件。进度条不再读取 Suite 的 `cases.length`。

前端可以在请求发出前用选择数量即时初始化，但收到 `suite_start` 后必须以后端值覆盖，因为登录准备可能自动增加一条用例。完成后的汇总继续以 `suite_done.total` 和 RunRecord 为准。

## Risks / Trade-offs

- **[API 同时存在旧 `case_id` 和新 `case_ids`]** → 入口统一规范化并拒绝同时提供，测试覆盖兼容路径，后续再单独弃用旧参数。
- **[queue 滚动升级期间新旧进程字段不一致]** → 新增列保持可空并保留旧列，worker 对旧记录回退读取 `case_id`。
- **[筛选后表头全选语义可能不明显]** → 工具栏持续显示总选择数，表头选择框只作用于当前可见筛选结果。
- **[Suite 内容在排队后变化]** → 执行核再次验证 ID；缺失或归属变化时整个 Run 失败，不允许静默扩大为全量。
- **[自动登录使总数大于用户勾选数]** → 确认文案提示登录准备可能自动加入，SSE 以实际有效集合总数覆盖前端初始值。

## Migration Plan

1. 先部署数据库迁移，为 `run_queue` 增加可空 `case_ids` JSON 列，不修改或删除旧数据。
2. 部署兼容新旧列的 API 和 worker；此版本既能处理旧单条任务，也能写入和执行多选任务。
3. 部署前端多选入口和新请求体。
4. 回滚时旧代码会忽略新增列，数据库列可保留；新多选任务应在回滚前停止领取或清理，避免旧 worker 将其误解为全量任务。
